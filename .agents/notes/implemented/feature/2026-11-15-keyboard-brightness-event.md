# Agent Note: 原厂138亮度事件的主动循环与报告同步

Status: implemented

## 问题

Arg001的138分支尚未接入，不能等同于现有亮度加减。FnKey.Form1对原始typeRule=22执行关闭→1→2→3→4→关闭，KBModule.typeRule直接来自WMI13 byte15；关闭只更新总开关，保留亮度。typeRule=1则经WhiteKB.GetBrightnessNow读取GetWMI(61)，其Brightness/Status setter同步page2[35]/[80]，不发送cmd39。此前“只读取并显示”的描述未包含保存副作用，本笔记更正该事实。

## 决定

- 新增独立keyboardBrightnessEvent授权，现有亮度、开关或状态通知许可不自动扩大。范围绑定原始型号、实际档位与共享开关能力，预览说明22型主动循环和1型报告同步；旧确认或设备变化拒绝执行。
- lighting/brightness_event拥有138规则。22型只发送必要F4和E0，保存35/80，不重放颜色或模式；关闭保留保存亮度。复用LightingController唯一首次基线、失败补偿与初始恢复，档案沿用同一灯光字段和基线。
- 1型读取61号时保留DCHU返回状态、回声和0–5有效值校验。page7 v1.0的WMI122 bit14仅区分0–2与0–5的屏显样式，不当作报告值上限；普通样式收到3–5仍同步缓存并刷新控件，但不弹屏显。hotkeys私有Completion分开携带结果与是否弹屏显，统一由runtime发布，不另开刷新路径。不猜未知能力版本，不用保存值代替本次报告。保存失败回滚35/80，不发送硬件命令，也不把固件已执行的按键动作登记为本软件硬件初始基线。
- 所有测试仅内存、函数桩、临时文件与模拟IPC；不读真实OEM接口、不触发按键。读取配置不执行138事件，恢复软件策略还原初始规则并由其决定后续接管；硬件初始恢复继续由既有灯光模块拥有。

## 影响与验证

灯光107项、热键19项及亮度事件跨域/整数ABI的5项检查通过，覆盖逐个档位、关闭保留、未知/不支持类型、无效报告、回声、能力变化、发送/保存失败、恢复重试及后续档案失败；白光报告同步零硬件命令且不新增硬件基线。相关模拟页面22项组合及最终4项检查通过，独立授权、预览确认、撤销确认、停止/恢复及深浅宽窄布局已覆盖；前端构建、主/模拟宿主编译已通过。最新Rust检查见target/ui-check/brightness-event-{lighting,hotkeys,profile}-final.log。

## 风险

61号整数通道在本机有已知回声缺陷，必须明确失败而不能制造可信亮度；其他固件仅在正确返回和声明档位内同步。保存回读不证明物理效果，原生路径只编译、不做真机验收。

## 备选方案

- 所有型号统一循环或统一只读：违反原版两个活动分支，拒绝。
- 用page2旧值代替失败的61号读取：会把旧保存值当作当前报告，拒绝。
- 报告同步创建独立硬件基线并恢复cmd39：会把固件先前执行的动作算作本软件写入，拒绝。
