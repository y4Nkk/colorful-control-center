# Agent Note: X170独立灯条

Status: implemented

## 问题

原厂X170灯条独立于普通RGB灯条和逐键键盘，现有外围灯区不能正确控制其模式、亮度与速度。直接复用cmd103会写错设备。

## 决策

- 来源为Pi会话中kbled 6.26的CC.Device.LightBar_X170及Page_LED_Device、FnKeyPack 7.19.5.0的LightBar_X170/Features，以及随原包LineLEDAPI.dll（SHA256 C77B9BE836E88218A9DCAFD5F17EDE0D918D7785FD9DE632B515D06D53C64D5A）。能力为page7 v1.0 WMI96 bit11；不能混用DTT bit12或普通灯条WMI122 bit12。
- 静态核对库RVA14d0初始化、1cbb能力检查、1710/1f80传输：VID048d/PID8297、usageCC/pageFF89，64B feature报告为CC、命令、62B数据。发送成功返回0，2是SetFeature失败、99是未初始化。自研直接使用严格匹配的HID传输及路径身份，不加载原库或复制其UI资源。
- lighting/lightbar拥有page2[108..127]的19字节、八种原厂模式及独立恢复基线；未初始化或未知保存值保留未知，不在读取时写默认。失去能力或设备身份变化保留基线并拒绝旧目标。普通键盘、外围和逐键字段不在该写集内。
- 草稿只编辑亮度/开关/速度/模式与对应颜色；目标保留未选模式的独立颜色。应用及恢复绑定当前字节、能力和HID身份，先预览确认，部分发送或保存失败独立补偿即时状态和保存块，首次基线在写前保留。
- 控制台使用自研灯条预览及左右模块卡片；无能力隐藏，读取失败保留草稿并撤销执行快照，恢复入口明确显示原始保存意图而非物理回读。保留未知当前值时允许在已确认身份上恢复既有有效基线。
- 本次调查还确认FnKey的USB选择性暂停读取cmd4/sub53后修改Windows活动计划，LAN相关分支委托cc30wk处理驱动；Deep S5仍只定位到sub57读取。继续追踪这些独立流程，不据此臆造固件设置命令。

## 影响与验证

8项原生内存检查通过，覆盖64B编码、八模式、颜色保留、能力隔离、旧预览、部分发送/保存失败、补偿重试、未知当前值恢复及设备替换拒绝。5项独立页面和灯条/外围/热键18项模拟页面组合通过，确认预览/确认/恢复、读取失败保留草稿并撤销快照、无能力隐藏和360/760/1440px布局；已目检灯条截图。npm构建、工作区与control-sim编译通过。原生测试的失败是临时RefCell借用在调用内持续持有，已改为先取独立修订字符串再调用，生产路径未使用该测试借用。

新增3项类型化IPC和独立控制台模块，HID只匹配已核对设备；没有替换现有普通灯条或键盘协议。读取时没有默认初始化写入，没有加载原库、枚举真实HID或执行硬件报告。全功能档案、TP及新多区灯条仍继续独立推进。

## 风险

保存意图和HID接受不表示物理灯条效果。初始保存值未初始化时无法承诺恢复此前未知的物理灯效，不自动接管。TP及新多区灯条仍需各自来源与协议。

## 备选方案

- 复用普通灯条cmd103：设备和保存区域不同，拒绝。
- 读取时照原厂初始化默认值：产生未确认写入及虚构基线，拒绝。
- 直接调用忽略错误的原库导出：无法可靠绑定设备及恢复错误，改为使用已静态核对的HID协议。
