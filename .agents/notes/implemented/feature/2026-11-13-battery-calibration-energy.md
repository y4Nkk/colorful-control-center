# Agent Note: 电池校准状态机与节能互斥

Status: implemented

## 问题

充电保护已接通，但BatteryPackUtility校准与EnergySave不是同一阈值设置。原厂校准由应用长期推进，直接绑定WPF页面和计时器，涉及模拟AC断开、Refresh与FlexiCharge；仅增加按钮或按电量百分比切阶段不能复刻实际行为。

## 决定

- battery域继续拥有充电策略，新增校准和节能子模块，互斥运行，复用HAL全局控制锁。UI只订阅阶段、供电事实和诊断，关闭或隐藏页面不改变任务生命周期；开始、停止和恢复分别预览确认。
- 事实源是安装载荷反编译的Page_Battery_Refresh、EnergySave.MainWindow及已核对FnKey.Features。校准顺序为Discharge1→Charge1→Discharge2→Charge2→AdjustingDischarge→Stop；BatteryStatus bit4/5驱动完全放电/充电事件，调整阶段按原厂StopChargingThreshold结束，不拿100%代替完整充电状态。
- 三个校准命令按原厂顺序执行：cmd121/sub28、cmd121/sub29、cmd118/sub7；均4字节LE且sub在byte3。放电阶段值为0/1/0，充电和调整初始为1/1/0，停止释放为1/0/1。调整阶段超过阈值才切0/1/0，达到阈值释放。
- 必须区分程序模拟AC离线与真正拔电事件。原厂在放电阶段本就预期Windows报告离线，不能以acOnline=false直接判断拔电并中止。继续核对原厂事件入口与读取证据后接入本应用调度。
- 已定位BatteryPackUtility.MainWindow两条真实事件入口：旧OutLog的Arg001值85/90/91分别是完整状态、真正拔电、完全放电；WM_COPYDATA的函数/索引268/270/273对应同样三类。需复刻生产者或受控订阅，不能把任意窗口消息当成可信任务状态。
- 本机已安装DCHUService.exe静态反编译进一步确认：DCHU.DoEventWork独占ACPI桥并把通知写为PowerBIOSServer_Out来源的OutLog/Arg001^N，运行标志是page1[12]。自研接收端只读订阅该日志，不另开独占桥、不修改原厂服务/日志/注册表；起点取订阅时末尾，拒绝历史重放、记录缺口、清空及畸形数据。事件只触发阶段判定，完整状态仍重新读cmd7；真正拔电优先暂停并释放强制放电。
- 状态机先独立落地并用内存通道验证；在独立任务握手、持久恢复和IPC/UI接通前不提供生产开始入口。状态变化每次只推进一个阶段，充电阶段先确认AC恢复，再把后续离线视为拔电；调整放电仅在阈值与电量均有效时完成。阶段命令首错停止，恢复分别尝试全部释放命令、原充电/节能策略及防睡眠请求，失败保留待恢复状态可重试。
- 原厂额外导入/切换/删除BatteryUtility电源计划。SystemRequired仅处理空闲防睡眠，不能代替该计划。包内batteryUtility.pow（SHA256 8ABCAE91FE798DB277C953E2A203B9EC4953BA94D08FA19F195DDEDEADF50151）由tools/probe/inspect-power-plan.py离线解析，生成15项设置、27个AC/DC索引；原始文件、索引和来源归resources/oem。确认屏幕常亮/亮度100%、睡眠/休眠超时0及临界电量1%等原厂参数，预览说明相应影响。解析不加载注册表或执行电源命令。
- 电源计划实现使用包内原始pow与由其生成的索引清单；两者绑定SHA256。开始预览修订捕获实际活动计划，任务操作标识派生本应用私有GUID；导入前确认目标不存在，导入后逐项回读原包AC/DC索引，再激活并回读。记录先于导入落盘，恢复先激活原计划，再删除本次私有计划及本应用资源副本，失败保留记录并重试；不使用原厂固定GUID或假定Balanced是原活动计划。
- HAL由app层绑定校准记录路径，模式/档案的电源计划预检与执行读取同一记录互斥；恢复流程也不在校准进行时覆盖私有计划。校准任务每次采样核对其活动计划，外部变化中止并恢复。所有电源API验证使用内存模型及临时文件，开发过程不调用真实导入/激活/删除API。
- 工作入口使用与Tauri一致的RoamingAppData Known Folder加配置中的应用标识定位记录，不从APPDATA环境变量建立第二条目录规则；已重定向的用户目录仍绑定同一份准备记录。
- 节能的保存、快照和恢复由已实现的battery/energy拥有，见implemented/feature/2026-11-13-oem-energy-policy.md；校准复用其恢复契约，不新建平行计划文件。不存在原厂保存计划时明确释放语义，不能伪造未公开的固件计划。
- 本机静态DSDT（SHA256 d5162a4a002576ad9dcc77115001fbc66801927d7890c1316b9839a3c14b5203）的DCHU.SCMD 0x76确认上述编码：sub3/4分别拆分钟/小时，不是任意分钟索引；原厂UI按整数小时保存，终点先加1。sub6会修改共享BSCP/BTCP充电阈值，校准/节能必须与现有充电保护共同恢复。
- 独立恢复进程在开始校准之前握手，父进程退出、断连或任务失败时释放校准控制并恢复已捕获策略。不能用原厂停止的固定释放值冒充“精确恢复未知前态”；先补齐可证明的初始状态来源、所有权和恢复语义再开放写入。

## 影响与验证

72项电池聚焦检查通过（含状态迁移、模拟AC离线、真正拔电、通知解析、原子恢复、临时电源计划和资源清理）。30项模式/性能选项和34项档案回归通过，另有校准记录阻止档案预检、已准备模式执行/恢复及损坏记录拒绝的跨域检查；21项电池/校准/节能/性能选项页面检查通过，包含校准期间模式互斥及解除、旧预览、切页、失败恢复和窄屏。npm run build与cargo check --offline --workspace通过。

calibration_process的7项真实隔离进程检查通过，复用生产Client、worker、Record、恢复事务和电源计划算法。覆盖父进程强杀、恢复重试持有租约、子进程先退出、活管道失去心跳、显式停止/完整五阶段、外部计划变化/部分导入及READY超时；模拟硬件和计划只写私有临时文件。未执行生产任务入口或真实电源API。

## 风险

ARM标记必须先落盘；电源计划确认目标空闲后，另将planPrepared意图先于导入保存。未接管的中断只解除准备记录，不发送硬件释放命令；未预留电源计划不删除同GUID的既有目标。恢复原计划失败时保留临时计划及记录，不能提前删除；恢复错误独立累计，供用户重试。生产Windows API仅编译，隔离检查不证明驱动响应、实际电池事件或充放电效果。

FnKey.Form1对低电量59/60事件另行执行电池控制；原厂clevobattery^207消息没有可用于自研事务的完成确认，且停止会异步EnergySaveInit。当前使用单控制者前置检查，原厂FnKey.exe或BatteryPackUtility.exe仍运行时不接管，运行中出现则中止恢复；保留DCHUService只读通知，不写原厂日志或结束其进程。此检查仅编译，未执行真实进程/服务/日志查询。

原厂将任务阶段保存在注册表，不能从UI阶段推定当前控制位。应用不修改原厂INI或注册表；实际充放电、耗时和事件传递仍需独立真机验收，不阻塞可确定代码的实现。

## 备选方案

- 只用电量百分比模拟校准进度：无法复刻原厂完整充放状态，拒绝。
- 原样复制页面计时器与固定Stop值作为恢复：退出链路和初始策略不完整，拒绝。
