# Agent Note: 逐键灯、独显关断与刷新率完整接入

Status: implemented

## 问题

用户明确要求把此前未接管的三项 OEM 功能完整接入，并保留预览、确认和恢复，不调试硬件。既有三区灯命令不能用于逐键 MCU；最初的反编译材料只看到 FnKey 独显动作委托 cc30wk，尚未读取助手内部实现。

## 决定

- 以本机 kbled/CC40 PerkeyKB、InsydeAcpiProt 和 perkey_api 原生二进制为协议事实，读取完整颜色矩阵及原始动态效果，逐键草稿使用同一灯光域下独立协议；跨页保存逐页预读、提交、回读及补偿。
- 逐键支持静态矩阵编辑、亮度和原始效果恢复；不把未知动态模式还原成单色。设备/传输未确认时拒绝写入；静态审查中不加载 DLL 或打开 HID。
- 刷新率按 FnKey DisplayManager 使用已枚举显示模式，绑定设备身份和当前几何，只切已支持频率；保存首次完整模式，提供应用前确认、应用后保留和超时恢复，失败保留可重试恢复记录。
- 独显最初使用Windows PnPUtil操作精确PCI显示实例。该代用路径已由[原厂NVPCF电源链路](2026-11-13-oem-nvpcf-power.md)取代，当前目标、固件顺序、策略恢复及权限边界归新笔记和oem-device-contract.md所有。
- 三项提供类型化 IPC、语义化预览、忙碌互斥与首次基线恢复；不悄悄添加自动模式、睡眠或电池事件写入。
- HAL文件拥有HID、Windows GDI和SetupAPI/CM传输，领域模块组合事务。耗时入口在后台工作线程执行；原厂GPU工作进程及提供者暂停语义由后续NVPCF笔记拥有。
- 显示写入与超时恢复复用 HAL 写锁；刷新率试用期间禁止独显 UAC，防止授权等待拖延自动恢复。原生模拟覆盖这一跨域屏障。

## 影响与验证

- 后续从本机FnKeyPack 7.19.5.0安装载荷找到cc30wk 7.0.15.0并完成NVPCF链路替换，原“助手缺失”前提已失效。真实协议归docs/oem-device-contract.md；本笔记保留早期PnP检查的历史范围，当前独显证据归后续NVPCF笔记。

- 20项原生聚焦检查通过：逐键7项、显示5项、独显7项、NVAPI连接失效与基线保留1项；覆盖跨页失败、动态恢复、旧预览拒绝、取消UAC、设备变化、回读失败、试用超时重试和UAC互斥。全部是内存提供者。
- 新设置页面27项、原有灯光24项及控制台63项模拟 IPC 检查通过，包括草稿保留、二次确认、错误、恢复和360–1440px布局；未运行完整测试套件。
- npm run build、cargo check --offline --workspace 与 verify-notes 通过；最终安装包仅构建和解包校验，不安装或启动真实应用。

## 风险

未执行真实灯光、PnP、显示模式或 UAC 操作。PnP 禁用是设备级关闭，不能声称已测得物理电源轨断电；驱动及固件的实际效果单独验收。

## 备选方案

- 只开放开关而依赖缺失助手：不能完成实际执行，拒绝。
- 猜测 ACPI GPU 电源寄存器或用三区命令驱动逐键设备：无协议证据，拒绝。
- 把整个应用常驻为管理员：扩大权限边界；仅单次已确认 PnP 操作请求系统 UAC。
