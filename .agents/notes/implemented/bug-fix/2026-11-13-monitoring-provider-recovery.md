# Agent Note: 监控提供者恢复与真实可用状态

Status: implemented

## 问题

Phase 1/4 的监控重试链路还有缺口：启动时 DCHU 或 NVML 初始化失败会永久保留 None，界面重试不能重新连接；dchuAvailable 依据 DLL 对象存在，而不是本次采样传输成功，可能在驱动失败时仍显示在线。

## 决定

- 生产 DCHU 在缺少连接时重新加载，仍持同一串行锁；已有连接的失败不在写事务中自动丢弃，保证补偿使用同一传输。测试不得退回真实 DLL。
- NVML 采样失败时释放失效连接，下次采样重新初始化；启动时暂不可用也可恢复。错误进入监控诊断，缺失数据保持空值。
- 独立监护的采样回调接收可变闭包，使用同样的 NVML 重连规则；已经见过 GPU 后的当次读失效仍立即触发自动恢复，不等待重连或自动重新接管。
- 本次 cmd12 读取成功才发布 dchuAvailable=true，失败时保留错误及空读数，不沿用旧样本。
- 2026-11-24 四通道监控统一为 `fan.cpu/gpu1/gpu2/sys`。原厂 `FAN.Read_FanSpeed` 分别以 cmd12 的 2/16/18、4/19/21、6/22/24、36/38/40 读取测速周期、占空比和温度。`ccc-core` 解码由桌面和探测复用，风扇页按选定通道显示，GPU 概览仍使用 NVML 芯片采样。
- cmd13 的存在位声明报告通道。原厂两点布局按 FANQ 的 1–3 路顺序识别，系统风扇须有明确存在位。通道在但停转时显示 0 RPM，未声明通道及无效温度留空。通道信息查询失败保留独立的 CPU 温度并发出诊断。

## 影响与验证

- HAL 内存 FFI 2项通过，覆盖成功→失败→恢复与无提供者不回退真实硬件。在线标记和缺失值随本次采样变化。
- 监护协议10项、独立隔离进程8项、软件生产循环与隔离监护组合5项通过；强杀的均为测试创建的模拟进程，恢复仅写临时路径。
- npm run build、cargo check --offline --workspace 和控制台63项模拟交互通过，含读数断连、停滞与重试。
- 本次的四路解码 3 项和四路页签的 Chrome 隔离检查通过，核对通道独立性、无效温度、通道缺失和真实停转。

## 风险

真实驱动重连效果未验收，本轮不加载原厂 DLL 或运行硬件探测。NVML 的故障恢复仍依赖驱动恢复响应。

## 备选方案

- 将所有错误当成 DLL 缺失并重载：会影响正在补偿的写事务，拒绝。
- 只更换界面状态文字：不修复初始化失败后永久不可用的实际逻辑。
