# 硬件架构与恢复语义

开发基准机：七彩虹将星 X15 AT 23（i5-13500HX + RTX 4060 Laptop）。UI 契约由根目录 [DESIGN.md](../DESIGN.md) 拥有；本文仅描述当前硬件通道和安全边界。

## 1. 控制通道

其他机型能力由`powerctl/mode/support`在读取、独立选项和执行入口统一判定。20720/20724的完整模式联动未支持：读取保留当前状态，编辑目标为空并给出明确原因；捕获不加入无法执行的模式或性能选项，旧目标不能绕过后端判定。不提供尚未落地的AMD中间计划编辑原型。

Windows模式恢复快照按计划保存首次ASPM值，后续模式事务只追加新计划，不覆盖既有基线；每次失败补偿仍使用本次快照。显式初始恢复逐项展示当前/初始值，实读值进入确认修订并在系统授权前后复核；不可读值显示未知并禁用恢复。严格持久结构为计划GUID到两种供电原值的映射，旧数组结构拒绝读取。

模式的Windows链路节能目标由`powerctl/mode/policy`唯一生成：v1能力page7[16] bit3使用分模式表；无此表且page7[11] bit1声明WMI96 bit9时，性能模式为AC/DC均0，其余模式均2。没有对应能力则不写，未知表值明确拒绝，不改用另一策略。两类目标都进入既有完整预览、模式事务、系统快照及失败恢复；不增加第二执行入口。

逐通道软件风扇闭环已经 PK04→EC C1 和 SCMD 0x69 接入，无需猜 GPU 0xE8。hal/firmware.rs 用 sha2 匹配已审查的本机 DSDT 哈希，只开放已确认的 CPU/GPU1；监护子进程独立核对该恢复能力，未核对就不 ARM。详见 oem-dchu-contract.md §8；社区 AT22 原始端口配置仅作历史线索。电源模式按 FnKey 接入 0–4（4 的即时值为 0），保留 Turbo/DTT；扩展能力下联动原厂分模式风扇、ASPM 和 Windows 电源计划。独显电源由设备卡片直接请求系统授权；自动刷新率经单独开关授权后可按已实现的普通模式及供电规则触发显示试用，特殊供电模式完成交接已接通；20720/20724等其他AMD机型明确标为未支持，契约见 oem-device-contract.md。

DLL ABI 由 hal/oem_dchu.rs 唯一拥有，探测 CLI 只读外观复用；返回值、包读额外复制空间与 0–15 页边界按审查过的本机二进制实现。cmd12 提供测速周期计数，ccc-core 按原厂最终 UI 公式换算为 RPM，不改变十级 RPM 表的数值含义。

`hal/power_events.rs` 是Windows电源通知传输的唯一所有者。自动档案和低温提醒可同时持有独立会话；每个会话使用自己的窗口类并自行注销，回调只向各自工作线程派发事件。低温提醒的授权、来源及状态见[电池契约](battery-contract.md#原厂低温提醒)。

DCHU 在启动连接缺失时可重试加载，已有写传输不因一次错误而重载；NVML 失效后下次采样重连。dchuAvailable 表示本次 cmd12 传输成功，不能用 DLL 对象存在代替在线。测试实例始终禁止回退真实提供者。

## 2. 模块所有权

- `hal/fan_safety`唯一拥有软件风扇的严格版本1运行/故障记录及退出接管资格，曲线和硬件恢复参数仍归原领域。首个输出前必须落盘，读缺失/损坏状态不写文件；强杀留下运行标记会在下次启动阻止自动重启。确认过的手动曲线可重建损坏记录，全部目标成功后才清故障；普通恢复和退出均保留故障。正常退出先撤销本进程曲线接管资格，再在HAL锁内释放并登记，晚到事务只做其余补偿，不重启曲线。

- `assembly.rs` 唯一装配原生领域状态，`lib.rs` 管理控制权及工作线程启动，`shutdown/` 唯一管理退出准入、收尾与最后期限。Windows 托盘的本地消息线程归 `tray/`。
- `powerctl/mode/supply`拥有原厂接电/断电及两种供电下的启动/唤醒六条件预览、通知调度和严格组合恢复；模式执行复用原模式/风扇/系统计划，频率执行复用GPU领域。原厂策略与自动档案串行提交且互斥，授权等待在HAL锁外，模式完成在锁释放前交接刷新率的真实上一模式。显式单项/热键/档案选择保存插电偏好，自动模式和仅性能选项不接管该字段。供电模式启用/继续检查六条件，运行事件只核对本次所属动作；唤醒不读取GPU调频策略或连接频率驱动。原生轮询只推进实际供电和通知调度，领取就绪事件后才按事件预检，避免外层全量检查提前阻断唤醒。EnergyStar已由公共模式事务统一，手动、热键及完整档案已接入同一GPU链路，启动与自动档案核对完整模式许可，原生通知与硬件效果未验收。

组合供电记录只接受版本3，模式授权摘要与GPU频率授权分开：后者绑定原厂策略及驱动设备/能力身份，关闭独显时明确延后的首次身份在写前原子记录，不能在唤醒或后续执行中自动替换。频率观察使用必填的判别结构（untracked、poweredOff、skipped及原因、ready及原始值）；跳过不查询驱动、不沿用旧读数，首次恢复基线保持不变。之后真正调频重新核对授权、物理设备和实际前态。只读预览另可报告unavailable及原始错误，保留其他实读与已知初始目标并禁止恢复；该观察不能持久化或成为写入前态，事务读取仍严格失败。`enabled`只反映保存的启用意图，`active`反映监听调度是否运行，各事件错误在执行前拒绝并由运行入口暂停；不把未来某一GPU条件不可读误报为用户已取消策略。

EnergyStar由`powerctl/mode/energy`唯一拥有解码及WMI79写入，公共`Target.energy`与`StoredModeSnapshot.energy`拥有目标和前态；只有性能选项时明确为null。供电记录不另存energy/targetEnergy，六条件不另算节能目标。模式顺序为命令、GPU调频、公共节能、模式后独显动作、系统计划、风扇；硬件P-state已声明时不发送79。显式首次恢复先检查能力，能力变化时所有域零输出并显示原因；事务失败补偿独立收集节能错误，仍尝试其余所属域。选项首次基线后发生模式选择只补入首次节能前态，恢复摘要随所有权扩展失效。原厂供电模式组合记录只接受版本3；开机档案选择由startup独立拥有，使用版本4完整许可。旧记录不会自动扩大输出许可。

`gpu_power/mode`唯一拥有模式独显Action/Stage/State和设备资格；供电模块只组装六条件，公共恢复预览不再引用供电模块的独显类型。客户端设备边界以OemModeGpuAction/State/Values表达同一契约，旧Supply专属类型已删除。明确选择可按已有自动关断偏好预览省电/安静增强关断，后台供电仅DCMode唤醒可关断；两者均保留自动关断偏好。该共享规则及公共执行已接入供电、手动和模式热键；HAL唯一初始模式快照保留实际尝试的节点与频率初值，恢复绑定当前完整节点、原始频率及驱动范围。完整档案、启动及自动规则已接入相同组合入口。热键循环逐范围保存稳定授权和首次驱动身份，实际事件重新生成完整单次目标，授权等待在HAL锁外。
- `hal/` 拥有 DLL/设备传输、硬件采样、全局控制锁与会话恢复记录；power_plan.rs 唯一调用 Windows 电源计划 API，测试只注入内存通道。
- `hal/screen_brightness`只读取唯一活动WMI面板及明确供电状态，`hal/wmi`统一COM连接生命周期。`hotkeys/screen_brightness`拥有原厂屏幕目标事件、计划AC/DC事务、可取消的有界执行及逐计划首次恢复；查询和等待在控制锁外，软件规则恢复不冒充硬件恢复，详见screen-brightness-contract.md。
- `hal/panel_inventory`按原厂精确EDID签名和设备实例只读识别215号事件的适用面板；部分节点未知不能推断为非OLED。`hotkeys/panel_hotkey`独立拥有预览、授权、屏保或一次性输入会话，以及只针对本软件资源的结束与失败重试；屏保用私有Job进程，钩子线程只上报活动类别，写入前重新核对来源和许可，详见keyboard-contract.md §20。
- `hal/monitor.rs`拥有当前采样和风扇解码。显示采样通过 `powerctl/mode::current_mode` 读取实际模式，归入 `HardwareSnapshot.oemPowerMode`，模式读取失败保留其他当次传感数据。`hal/memory.rs`只解码原厂共享报告中的内存频率/参考值，归入HardwareSnapshot.oemMemory。cmd12本次失败不读取旧共享报告；单项读取失败不清除本次CPU/风扇成功值。系统容量仍由overview独立拥有，报告频率不冒充直接实测或DDR有效速率。
- `hal/msr.rs` 唯一创建桌面 MSR 会话；生产打开 PawnIO，测试只接受显式内存传输，不能退回真实设备。
- `hal/key_events.rs`唯一拥有低层键盘事件生命周期，灯光与显式宏录制复用；`hal/event_log.rs`唯一拥有经典日志只读传输和记录校验，校准通知与宏程序事件各自选择领域消息。读取配置不安装钩子或开启程序监听。
- `keymap/`拥有原厂活动配置只读解析、映射保存/恢复记录及程序宏监听；过滤器没有映射表getter，不能将保存意图冒充回读。首次原配置和原始启用标志在任何驱动修改前持久记录，Prepared状态不允许新映射或启动程序。详见keyboard-contract.md §10。
- `hal/oem_owner` 统一检查原厂控制进程。手动预设切换可确认关闭唯一匹配的原厂 FnKey，身份由 Windows 应用 ID、包目录中的实际映像、会话、进程 ID 和创建时间核验。确认绑定模式目标修订，通过 `WM_CLOSE` 请求主窗口执行退出流程，在 HAL 写锁外等待进程退出。随后模式事务重新检查原厂占用和完整目标。热键、档案、恢复及自动策略继续按原有互斥要求执行。[Windows 应用 ID 查询](https://learn.microsoft.com/windows/win32/api/appmodel/nf-appmodel-getapplicationusermodelid)
- `hotkeys/`拥有严格版本化的接管策略、授权范围、首次软件策略基线和串行事件生命周期。控制动作复用领域事务，另有独立stateNotifications和cameraReports范围；notifications只生成原厂报告，数字锁条件委托hal/keyboard_inventory只读查询。camera_report唯一拥有page1[6]事件镜像及逐字段失败补偿，不执行设备开关或建立硬件基线；两类反馈不触发硬件控制刷新。临时停止不恢复硬件；`osd/`拥有独立窗口及显示计时，不改变硬件结果，契约见keyboard-contract.md §11、§18、§20。
- `gpuctl/turbo`拥有96/97事件目标预览、跨显卡预检、原厂顺序执行及独立锁频恢复；与单项及档案共用`GpuController`和设备身份绑定的首次偏移基线。锁表只发送原厂两个目标域，不把其他GPU或非所属锁频域纳入写包；供电或目标变化停止后续输出，失败按本次前态逆序补偿，详见nvapi-contract.md §9。
- `ccc-core` 拥有 MSR 编解码、AppSettings 字段事务、曲线校验和监护触发判断；桌面与探测 CLI 复用。
- `fanctl/`、`powerctl/`、`gpuctl.rs`、`gpu_power.rs`、`graphics_mode.rs`、`display.rs`、`lighting.rs`、`keyboard.rs`、`battery.rs`和`platform.rs`拥有对应领域行为；`commands/`只校验参数并调度。
- `lighting/multizone`独立拥有type23的cmd4/sub44、模式/速度/亮度/开关及四区/灯条/顶盖颜色；闲置和开机覆盖继续由options拥有。单项、亮度热键及完整档案共用Scope和首次基线，部分及后续失败只恢复所属保存字段。独立HID灯条如同档案存在，明确在多区设置之后发送其效果。

- `lighting/lightbar`独立拥有X170的page2[108..127]、八模式和恢复基线，`hal/line_led.rs`只执行已核对的64B HID；能力与设备匹配后才开放，未知保存值不在读取时初始化。与普通键盘、逐键、Logo/普通灯条的写集分离，详见keyboard-contract.md §12。
- `touchpad/`拥有完整识别节点集合、Windows实际开关和原始OEM偏好；单项、252/253授权热键与档案复用Scope/Plan。hal/touchpad只识别、读取和发送系统组合键，未知状态拒绝写入，见touchpad-contract.md。
- `lighting/color_cycle`复用普通灯光基线，拥有57号事件的调色板与page2[127]序列位置；仅尝试写该字段时纳入首次恢复。HAL只读SMBIOS厂商，测试缺失明确注入时禁止回退系统查询；不建立第二个档案颜色字段。
- `lighting/brightness_event`拥有138号的22型主动循环及1型报告同步。主动循环只改亮度/开关，复用唯一灯光首次基线和档案字段；白光报告仅同步缓存、不发送cmd39、不登记本软件硬件写入基线。型号、档位与共享开关能力绑定独立授权，61号整数回读必须通过状态/回声/范围检查，不从旧缓存伪造报告。
- `microphone/`拥有活动录音端点目标和原厂静音偏好；单项、38号热键及完整档案复用Scope/Plan和首次基线，hal/audio仅执行Core Audio传输。读取不初始化保存偏好，详见microphone-contract.md。
- `profiles/apply.rs` 拥有跨域预检、执行和逆序恢复；`startup/` 与托盘复用同一档案实现。
- `controller_lease.rs` 拥有跨进程控制权：全局 Windows 对象由主进程独占建立，监护在 READY 前保留同一对象句柄；最后一个句柄关闭前不允许另一主进程接管。
- `battery/calibration/power_plan.rs`拥有校准计划生命周期，native.rs仅导入/校验/删除本次私有计划，活动计划操作复用hal/power_plan；原始pow及其离线索引绑定SHA256。HAL绑定唯一校准记录路径，模式/档案在未恢复期间不得覆盖计划。

`powerctl/mode/links`唯一拥有GPU模式的Context、保留Session与组合Plan：在节点输出前复核核心模式、GPU策略、节点和原始频率；依次处理前置节点、写前调频检查点、公共模式命令、调频、EnergyStar后的节点、系统计划及风扇。失败按模式后节点/频率、核心模式、前置节点的依赖顺序补偿。供电Native只提供规则与持久检查点，不再保留节点或调频的平行执行实现。GPU原始观察、首次频率基线及来源由`gpuctl/turbo/mode`拥有，供电记录仅拥有其事务校验和采样范围。明确选择、热键和完整档案共用该完整入口；启动及自动规则绑定未来AC/DC目标和首次驱动身份。

原厂quiet_plus在独显原已关闭时，模式命令后等待1000ms，再继续GPU/EnergyStar。公共Plan保留该分支，以单调时间和20ms许可检查实现等待；取消仍执行公共补偿。其他模式、在线节点或无节点不额外等待；等待不等同于已经验证物理硬件稳定。

页面由 `src/app/navigation.ts` 登记。系统设有概览、风扇散热、性能调校、配置档案四个标签，设备配置集中显示、显卡及设备开关，键盘与灯光集中键盘和外围灯效、映射与宏、原厂热键与屏显。电源集中电池与充电、节能与校准、启动档案、供电与唤醒规则及设备电源策略。托盘选择档案时打开系统的配置档案标签和预览。共享采样和恢复状态由应用与原生领域所有者保留。

## 3. 写入流程

滑杆和曲线拖动更新草稿，查看差异后由用户请求写入。设备配置由选择和开关直接提交，提交后回读。忙碌时禁止重复请求，初始恢复在所属模块执行。各硬件写入口通过 `Hal::begin_write()` 串行化。

托盘使用后台回读生成原生菜单和悬停状态。点选预设复用性能调校的完整事务及原厂 FnKey 确认。会交还软件风扇控制时先说明影响。风扇全速确认绑定当时的预设、风扇档位和软件曲线，应用前重新核对。交还固件控制沿用风扇域的安全释放与原厂自动策略。确认等待期间允许退出，硬件事务纳入退出准入和写锁。执行后回读当前值并通知主窗口刷新。

LAN和独显系统授权共用hal/authorization的保留会话协议：领域互斥覆盖整个操作，HAL锁只覆盖前后预检及实际执行，不覆盖用户授权等待。子进程就绪后等待父进程许可，父进程重新核对来源和运行互斥再放行；许可前取消或主进程退出不访问设备。请求和补偿仍由各领域拥有，独显许可前不加载DCHU。测试环境必须显式注入对应环境及授权会话，不能回退原生提供者。

控制台收到退出请求时停止接入新的 IPC 与后台工作。已进入的 IPC 在同步处理器或实际阻塞任务内持有同一退出准入，覆盖硬件锁外的预检、授权提交和失败补偿。自动调度先撤销许可，随后等待其工作线程结束。清理线程停止热键、宏及逐键监听，释放软件风扇、显示试用和电池校准，再请求框架退出。Windows 会话结束同样等待该收尾。

首个请求启动 15 秒的 Windows 内核计时器，重复请求沿用原期限。独立退出监护只持有控制台直接复制的计时器及主进程句柄，等待主进程自然结束或到期后以 124 请求终止。监护先于硬件装配启动，普通退出和 DLL 卸载仍在期限内，风扇、显示、电池及授权监护各自按现有恢复协议处理。Windows 需完成或取消内核 I/O 才能完成进程终止。[Windows 进程终止语义](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess)

独显授权文件只接受完整Sequence：1–3个连续阶段共同绑定同一摘要及一个工作进程，每阶段许可前重新核对冻结文件。节点/自动关断值及问题码可由前一目标明确投影，设备身份、显示用途和能力不猜测。共享协议在两端限制执行次数，LAN保持一次；独显序列失败或恢复后不能继续输出。工作进程统一拥有每阶段任务，取消、父进程退出及提前提交未完成序列时逆序尝试全部已修改阶段；恢复失败保留每阶段错误并可用原会话重试。Scope结束授权会话之后才释放领域互斥，单阶段也走同一格式和执行路径，旧单Request文件拒绝。

AppSettings 只改请求字段，先预读全部目标，写后回读；失败恢复目标和原触发字节。page6 的跨域快照和首次基线包含 IsSaved，恢复时最后写回原值。读取失败禁止写入，保存值与实际值分开，不能把保存成功等同于即时生效。

PL 35–157 W、PL1≤PL2；page6 保存整数，MSR 按 RAPL 单位编解码，保留捕获读数精度。控制台电压输入为整数 mV（核心 −150…+50、GT −150…0），运行时目标使用对应的原始编码边界。一次 CPU 确认只发一个请求，全部字段共用预检/执行/恢复事务；写前记住基线，检查锁和 Mailbox busy/status，失败按原始 PL 字段及电压编码恢复并回读。

请求的 CPU 编码与当前值一致时只确认现值，避免重复目标写入；锁定但一致的 PL 允许档案其他域继续，有差异仍拒绝。恢复也可通过确认原编码完成。这些成功结果不证明硬件可写。

GPU 偏移采用驱动范围与应用范围的交集（核心 ±300、显存 ±1000 MHz），不放宽未报告的范围。事务及档案回滚保存原始 kHz，避免 MHz 往返取整。首次成功修改前的逐域基线供用户恢复。

模式预检同时读取原厂联动目标并捕获风扇与 Windows 策略，修改前登记首次基线。预设卡片激活即提交已读目标及修订，手动档案提交已预览目标。后端均重新校验完整目标，策略变化时拒绝执行。失败独立尝试模式、系统和风扇恢复，档案的即时 CPU 在模式恢复之后按原始编码还原。ASPM 按原厂顺序修改原活动计划，再激活目标计划，恢复保留原 GUID 及原 AC/DC 数值。

模式事务持有 HAL 写锁，调用方许可在 DCHU 锁外检查。DCHU 锁只覆盖各设备步骤。EnergyStar 将前态核对、命令和回读放在同一个 DCHU 锁作用域。实际除尘状态由模式事务和风扇域在预检、执行和恢复时核对。

原厂模式域拥有 Turbo 风扇与动态调校 DTT 偏好，CoreSnapshot 捕获两个原始保存字节和待恢复的模式命令。已核对的固件以实时命令门控确认娱乐档支持，命令保留档位编号 3。DTT 另校验当前已启动的 ACPI 调校设备。其他固件沿用原厂标记确认选项。娱乐与性能模式各自按能力开放寂静模式，启用 Turbo 时切换到自动风扇策略。娱乐档可确认从自定义固件曲线交接给 Turbo，风扇快照保留初始曲线及关联的寂静偏好。独立选项校验关联的系统计划前态，完整模式切换管理 Windows 计划与 ASPM 的联动写入。详见 oem-dchu-contract.md。

档案 `performanceOptions` 在可激活的模式将所选位合入组合预览及首次模式命令，其余模式保存偏好。仅选项必要时临时释放软件曲线并按最终目标恢复。全量预检拒绝 Turbo 风扇与曲线或寂静模式的冲突，激活动态调校 DTT 时确认驱动。执行前复查来源风扇及所属的 Windows 快照，局部补偿成功后各域沿用自己的恢复状态。启动预览的授权绑定当次联动目标。

## 4. 风扇安全

1. 固件方式按能力选择固定锚点加两点或十级 RPM 表，保持各自约束；软件方式每把 2–12 个整数点，温度 20–95°C 严格递增、占空比 20–100% 不降、末点 95°C/100%，回差 0–10°C、斜坡 1–100 百分点/秒。自由曲线不压缩为固件两点，不改固件表。
2. 原厂预设、风扇档、偏移、固件曲线及其恢复由固件执行。应用只在持续写占空比的软件曲线中启动同一 exe 的 `--fan-watchdog` 进程，完成 READY/ARM/ARMED 握手后才输出。构造阶段完成 READY，HAL 登记唯一句柄后发送 ARM，ARMED 回报失败时保留句柄并进入待恢复状态。
3. 心跳由独立线程发送；软件模式还检查上一次完整输出进度，超过 3 秒则关闭监护输入并取消后续输出，不能由 UI/采样线程存活掩盖停滞。软件调度每 500ms 使用 CPU/GPU 较高温度，GPU 通道初始缺温度时不接管；任何时刻出现过的 GPU 后续丢失、CPU 失效或温度达到 95°C 都恢复。CPU 使用本版本原始温度直通分支。
4. 父进程同时检查子进程与回报管道；输出连接断开也触发补偿恢复。未 READY 的子进程在超时后结束并回收，尚未发送 ARM 时不写硬件。恢复报告遇到父进程已关闭管道时不因 BrokenPipe panic。
5. 软件监护恢复期间保留子进程句柄并禁止新的风扇目标。父进程确认子进程退出后在控制锁下补偿恢复，失败时保留错误并重试。正常切回固件时先释放逐通道输出，确认监护退出后再交给固件。解除失败进入待恢复状态。
6. RPM 表按风扇自身最大转速换算；保留热保护、升降速参数和未修改的伴随表。成对包逐表回读比较完整原始字节，失败回滚并保留恢复错误；原厂默认恢复可写其固定停转表，结束于自动模式。
7. 固件风扇操作先释放软件会话；恢复自动在已核对型号先用 0x69 掩码释放 CPU/GPU，再执行原有自动模式与保存回读，每个恢复阶段独立尝试并保留错误。恢复失败停止心跳并安排父进程重试，不让已停止的控制循环自动重启。用户初始恢复包括模式、曲线、保存字段和偏移，不能猜基线。
8. 父进程与已 ARM 监护共同保留控制权对象。父进程被强杀后，旧监护恢复结束前，新主进程不能初始化硬件或执行写入；监护先退出时，存活父进程仍保留控制权。进程退出由 Windows 关闭句柄，不创建陈旧锁文件。
9. `fanctl/dust`拥有原厂固件除尘与计划。普通曲线、模式、偏移、默认/初始恢复，以及模式和档案预检均先核对实际除尘状态；安全熔断及监护恢复不受普通互斥阻挡。软件曲线要求除尘计划已明确关闭，反向启用计划也拒绝软件接管。前端风扇事实返回`blockedReason/softwareBlockedReason`，预设模式和性能选项复用相同原因；草稿可编辑，执行确认随互斥变化失效。

监护状态机与父进程客户端分别由 watchdog/protocol.rs、watchdog/client.rs 拥有，watchdog.rs 只组合实际传感/恢复出口。隔离测试复用这两部分，并用真实进程强杀验证父进程消失后的链路；恢复出口为日志，独立监护仍依赖驱动和 OEM 传输响应，不能据此证明物理散热或底层阻塞时的效果。

扩展 IFSC/RPM 模型的 page4[70..78] 记忆每个电源模式的风扇模式/偏移；模式0与4共用槽0，全速只在当前生效、记忆为自动。两点/RPM/模式/偏移共同维护槽位，事务与初始恢复包含这些字段。两点固件默认恢复先捕获旧曲线，重置后从原厂包读出默认并同步保存值；失败补偿，成功仍可恢复首次基线。

## 5. 档案与启动

显示档案由`profiles/application.rs`协调，保持现有领域Scope→HAL顺序，显示状态仅在HAL内短时访问；不持硬件锁等待用户确认。全域预检后先试用全部变化屏幕，15秒内明确保留才重新预检并执行其余目标。保留后的本次恢复资格阻止独立显示/显卡操作穿插，系统授权等待仍在HAL外，来源变化停止输出；失败恢复本次显示前态，成功释放资格。捕获/文件/预览/应用共用`display/profile.rs`契约，单项和档案共用首次显示基线与批次监护。返回结构区分完成步骤与待确认，启动结果随继续、取消和超时更新；MUX重启仍是独立确认。详见oem-device-contract.md。

根事务的`Outcome.targets_applied`记录全部目标是否确认，IPC返回`targetsApplied`，监听/授权收尾错误仍保留在步骤中；显示提交依据该事实，设置失败才补偿。前端仅由全局执行store持有结果，以独立的最近应用卡展示实际执行的档案，预览不另存步骤。启动最近结果直接读取应用Controller，后续手动应用保留上一启动结果；初始启动线程只记录建立会话前的错误，不再缓存同一结果的另一份文字或发送旧的未消费事件。

应用报告以`origin`唯一表示manual/startup/ac/battery/resume，不再输出startup布尔。自动来源必须携带内部执行权限，显示待确认会话保留同一权限；普通保留入口不能移除它。候选准备、系统授权前后及设备阶段之间复核执行权限和档案文件，失效记录具体错误并沿原事务补偿；恢复不依赖仍有效的执行许可。最近自动结果与最近启动结果均由应用Controller拥有。供电及睡眠策略由profiles/policy拥有，已接入应用监听、串行调度和控制台；原生回调只访问事件内存，通知失败立即撤销执行许可，配置读取不隐式接受外部启用意图。报告文案与后台日志由application统一拥有，启动与自动流程复用；契约见docs/power-profile-policy-contract.md。

档案 schema、版本、名称和数值由 profiles/model.rs 统一拥有。fanSoftwareCurves 与 fanMode/fanCurves/fanRpmCurves 互斥，两点与 RPM 表也互斥。软件方式捕获实际会话配置，回滚重新启用精确原曲线；预设模式的原厂停转表不伪造成手动目标。

档案创建按性能与散热、显示与显卡、灯光、充电与供电、设备功能选择范围。capture 只读取所选配置组，在领域 Scope 与 HAL 的既有锁顺序内捕获。组范围由档案已经包含的字段派生。手动预览使用应用事务的预检，读取当前值用于差异展示，缺读时仍展示档案目标。原厂模式联动由事务计划提供，显示、独显及显卡模式复用各域预览。

profiles.rs 拥有 `profiles/<档案名>.json`，startup/mod.rs 拥有 `startup-profile.json`；文件均在应用数据目录。保存/导入档案和启动选择先校验、序列化，再由 storage.rs 在同目录暂存完整内容、sync_all 后原子替换；提交前不打开或截断原文件。Windows 提交遇到错误 5/32 时保留同一临时文件，最多额外重试 8 次、每次间隔 5ms；最终失败保留原文件和原始错误。正常失败清理临时文件，强杀可能遗留的 `.tmp` 不进入档案列表。设备保留名称（含 COM¹/²/³、LPT¹/²/³）拒绝作为档案名。该机制未验证断电恢复。

档案保存拒绝 Windows ordinal 比较相等但拼写不同的文件名，避免大小写覆盖破坏文件/JSON 身份；不添加别名读取。删除与保存串行，删除先解除匹配的开机选择，再移除文件；失败恢复选择，恢复失败明确报告当前安全的未选择状态。启动选择的保存和解除共享互斥。

新档案要求名称空闲。覆盖和删除在档案文件锁内核对列表给出的内容修订。导入先解析并校验，再走同一个保存入口。后台规则使用同一修订摘要绑定所确认文件，覆盖后在电源页预览并重新保存规则。

`runtimeCpu` 由 powerctl/runtime.rs 拥有，PL 使用 W，电压保存 coreOffsetUnits/gtOffsetUnits（每单位 1/1024 V）；与顶层 OEM 保存字段分开。捕获不将实时值取整为保存值。导入先预览确认，手动应用携带完整已预览档案，与磁盘当前内容及版本/时间戳比对，并绑定已预览的模式联动目标，变化就拒绝目标写入；时间戳限定于 JavaScript Date 可表示的整数毫秒范围。

所有涉及域先校验文件、可读取能力和快照，授权等待在HAL外。独显关闭时仅先开启该节点，再检查档案所需NVAPI范围和GPU温度；动态复核失败恢复独显，不执行其余设置。随后按除尘关闭、OEM模式、风扇、保存值、即时CPU、平台配置、除尘启用、键盘/灯光/映射、独立灯条、GPU偏移和独显关断执行目标。MUX选择请求在最终复核前发送，运行的软件曲线临时释放后恢复；独显和显示最终复核后才交接事件监听。失败先恢复本次MUX选择（如有尝试），再恢复独显节点/策略，再恢复可捕获的原始GPU kHz，之后按原依赖恢复灯光、平台、模式、CPU和风扇；恢复某阶段失败仍继续其余阶段并明确报告。原本关闭的GPU没有可读取偏移，不虚构关闭前数值。

`lightBar`是严格kind/settings型号契约，`dustSchedule`是星期/整点/唤醒配置；null表示不修改该域，灯条保留未选模式颜色和共享字段，除尘不保存一次性启动动作。支持除尘但未报告原计划时，捕获明确失败，不默认填关闭计划。执行检查点与单项操作共用控制器的首次基线，局部补偿成功不重复全局恢复，局部补偿失败由档案再尝试。

`keyboard`复用固件前三项nullable功能状态，null表示原厂未提供该项；`keyboardLighting`绑定keyboardType、独立enabled和当前LightingRequest，保留关闭时的非零档位；`lightingOptions`绑定keyboardType和原选项Values。型号、能力、支持字段及完整组合均在写入前校验。两类灯光恢复只合并本域字段；外围步骤允许同一档案先改变键盘亮度/颜色，执行时仍重读共享掩码，不能重复使用预检时的旧全局开关。

Devices/Scopes按除尘、独立灯条、多区键盘、键盘功能、普通灯效、灯光策略、逐键、映射、PD、USB、电池、LAN、独显、显卡选择、HAL全局写锁的顺序获取，领域内不再次获取HAL。独显准备/执行/本次恢复沿用同一Scope和授权进程，读取不登记基线；阶段内只短时锁显示状态。性能选项由HAL模式域编排。捕获、预览、应用及恢复在后台运行，单项与档案遵守同一锁顺序。

lanPolicy保存能力、逐设备完整驱动身份及适用的固定字段，原始类型/字节和缺失状态完整往返。全量预检后在HAL外准备同一次授权，再全量预检并核对文件及许可绑定；建议仅填草稿，不是目标修订权威。执行/本次补偿共享保留的工作进程，逐尝试字段持久登记初值，恢复不覆盖外部值或文件。局部恢复成功不重复外层补偿，后续失败先恢复LAN再恢复模式/原始风扇。LAN步骤可安全释放并恢复当前软件曲线；释放失败不继续网络写入。授权收尾在HAL外，失败单独报告，不隐去已确认目标。

即时 CPU 基线在档案首次写入前登记，即使更早执行的模式改变 CPU 后、保存步骤失败，也保留可重试的原编码。OEM 模式基线也先于命令登记，命令及补偿均失败时仍可再次恢复。

`perkeyLighting`绑定keyboardType、完整MCU/布局事实及Values，与普通灯效目标互斥；外围策略型号必须一致。读取/捕获不启动事件。逐键目标先执行一次全域只读预检，在HAL锁外准备未激活候选，再持锁重新预检所有域和手动确认文件；候选失效或CPU/设备等条件变化时零目标写入。逐键步骤暂停原会话，GPU等全部步骤成功后才激活候选；输出等待HAL释放。失败先恢复原始保存/即时灯效，再恢复原本运行的会话；原本已失败或暂停的不自动启动。线程销毁、旧会话Join和归属提交都在HAL释放后执行。初始恢复保留填充及非活动所属字段，计时/外围等当前非所属字段保留；成功才清除同一首次基线。

映射的读取、应用、恢复、监听重试和热键统一经keymap/scope.rs取得领域锁，再取得HAL；原有Store仍唯一拥有持久基线。隔离Controller必须注入映射IO，缺失时拒绝，原生配置与过滤适配器不编入该测试路径。映射档案使用keymap的configuration/programsEnabled目标；有接管记录时仅捕获owned设备，启用位取当前保存标志。原transaction::apply/restore已替换为唯一Plan、Prepared执行、最终commit和本次rollback，单项、热键与档案共用。程序候选锁外准备，映射步骤暂停原监听，GPU及逐键激活均成功后才提交Applied并激活候选；工作线程取得已释放的HAL后丢弃积压日志再消费新事件。失败恢复原记录和原运行会话，原本失败的不自动重启；原Prepared的实际映射未知，显式初始恢复失败保留记录，不重放保存意图冒充前态。线程交接与Join都不持HAL。

档案启用程序监听须展示新会话涉及的全部owned设备；缺少设备的文件在任何目标写入前拒绝，不借局部配置启用未预览的宏。局部与外层补偿共用事务内的记录修订/能力/来源检查，变化时不先恢复过滤器再报告文件冲突。单项请求通过完整当前Frame的expectedRevision绑定已有上下文，不另建执行器或恢复记录。

`powerDelivery`绑定等级、legacyZeroBased/legacyOneBased/adapterV1编号、适配器报告和有序候选；预检严格核对，执行再检查本次快照。`usbPolicy`按标准计划保存AC/DC目标，null保留字段；缺失计划或未知被选字段拒绝，捕获不压成统一布尔。模式预检给出USB执行后允许的活动计划，执行核对固件、计划值及该计划；本次补偿仅还原实际尝试字段并刷新实际活动计划，之后再恢复模式。PD/USB沿用唯一首次基线与单项事务，局部恢复成功不重复外层补偿，失败保留写集供外层再试。USB隔离Controller无显式IO时拒绝，测试不回退系统电源或原厂进程枚举。

`batteryCharge`携带原始开关/阈值及候选，关闭快照可精确重放0/0；`batteryEnergy`携带完整计划和能力。活动计划只捕获节能目标，不创建手动阈值冲突；停止计划先恢复stopCharge，再应用已预检的独立阈值。电池Scope与单项共用首次基线，节能准备/执行/提交及本次恢复使用同一持久Record，记录或能力变化停止旧输出并保留诊断。校准始终独立，待恢复记录阻止电池捕获和应用，档案不触发充放电任务。详见battery-contract.md。

档案列表与预览各自维护请求代次，写入使旧读取失效；托盘请求在写入后消费最后一个，不重复消费旧请求。控制台变更后只刷新其他受影响域，保留未提交草稿和操作模块自己的错误。

未启用策略时，普通打开应用不写入硬件；此前明确启用且授权条件匹配的热键策略恢复监听，按各范围已预览规则处理物理事件与启动检查。面板维护范围包含适用NVSR启动修复，低温与低电量范围沿用各自启动检查，不能概括为仅物理按键执行。只有通过注册表的显式 `--autostart` 启动且用户已确认启动档案时，才自动应用档案。启动选择只接受版本4和可空Binding，绑定完整文件摘要及稳定模式Grant；其他版本拒绝且保留原文件，不升级旧许可。同名档案修改后须重新预览确认，不能以名称授权最新任意配置。保存比较完整文件和未来AC/DC模式授权，返回后端规范Binding；首次延后驱动身份在调频前持久登记。启动与自动来源均须内部执行权限，系统授权前后、显示保留和设备阶段间重新核对；详见power-profile-policy-contract.md。

启动模式选择明确包含插电偏好保存，电池供电时同样执行；列表与当前选择独立读取，保存状态未知时保留草稿并允许明确重新选择或取消，初读未完成不开放保存。软件开机启动开关由设置页拥有；主窗口可见性由启动时最小化偏好唯一决定，偏好读取或执行失败时显示恢复界面。托盘点击档案只唤起预览，不能直接写硬件。

`startup/launch.rs`唯一拥有启动档案建立会话前的错误与准备令牌；准备在派发线程前登记，完成、失败、放弃派发或异常展开均释放。实际应用会话及待确认显示仍由`profiles/application`拥有，其忙碌查询不等待事务锁，并能观察已到期的显示试用。原厂模式和自动刷新率首次恢复等待准备与档案会话结束，后续后台输出也在档案应用期间等待；自动档案只等待准备阶段，已有试用撤销继续执行。模式首次恢复只领取一次，显式启用/继续/暂停/恢复均消费该机会；代次核对与重新入队在同一共享锁内完成，等待期间的暂停不能被启动恢复覆盖。监护、显示恢复及通知收集不随准备阶段停止。

软件渲染偏好的重启只传 `--restart-interface`，不继承自启参数；新进程在单实例插件和硬件初始化前等待原主进程与监护释放控制权，取得的同一租约直接移交控制插件。超时拒绝接管，不在软件重启时重复应用机器档案。

Tauri 官方单实例插件首先初始化；硬件控制插件随后取得全局租约，再创建 HAL/GPU/灯光控制器，均先于窗口与启动档案。重复普通启动只显示现有窗口，重复自启不显示窗口、不再次应用档案。监护分支先于 Tauri，保留租约成功之后才加载传输及发送 READY。

## 6. 验证范围

系统睡眠、休眠、显示关闭与关机的Win32原语由 `hal/system_action` 唯一拥有，低电量及合盖域只提供已核对目标。飞行模式专属设备协议归 `hal/airplane`，CUI固定面板请求归 `hal/panel_aux`；上层分别拥有预览、授权与恢复语义。手动飞行模式与133热键共用Controller及首次恢复基线，不建立第二套系统状态。原厂面板维护范围明确包含接管激活后的适用NVSR修复；浏览页面与准备监听不执行该请求，激活后与后续事件逐段检查已确认许可。

构建、原生聚焦单元测试、核心测试、生产模块模拟、隔离进程测试和浏览器模拟 IPC 均可离线执行。Windows 资源由 Tauri 生成图标/版本，windows.manifest.xml 唯一拥有 Common Controls v6 依赖，独立清单资源链接到应用和 lib 测试，避免仅 bin 带清单。本轮不执行硬件写入、驱动安装、提权或重启。尚待真机验收的项目由 [acceptance-checklist.md](acceptance-checklist.md) 维护；不因模拟成功宣布硬件已生效。
