# Agent Note: 风扇加速偏移的档位与机型门控

Status: implemented

## 问题

寂静档调偏移曾有「未见转速变化」的口头反馈，没有同负载对照。把现象直接推断为
「寂静档不消费偏移」，控制台因此在寂静档也禁用了滑杆。原厂 FanSpeedSetting 的
寂静选项并不隐藏偏移：开关与偏移分别发送风扇档位和偏移命令，FnKey 恢复寂静时
也会先下发已保存的偏移。仅按单一现象禁用，与已确认的原厂设置行为不符。

## 决定

- 风扇域是手动偏移许可的唯一所有者。自动及受支持的寂静档可调。RPM 布局、置位的 WMI96 bit10、未知能力、软件接管及除尘均阻止手动偏移。前端直接消费后端的禁用原因。
- 手动 IPC 在 HAL 写锁内重读设备，核对提交的档位，再写偏移命令和 page4 偏移字段。拒绝时不登记基线、不切换或停止风扇控制、不写固件。
- 原厂预设的联动偏移由模式事务调用既有固件写入逻辑，档案、恢复与寂静档保存模型沿用原有契约。

## 影响与验证

- 界面：`fan-visuals.spec.mjs` 覆盖自动与寂静可调、寂静提交只发一次偏移且回读
  仍为寂静、其余档位与不支持机型保持禁用且不发送偏移写入。
- 原生：`fanctl::dust::tests::native_tests` 覆盖布局与 WMI96 两种能力禁用来源，
  以及寂静档正常设置只更新偏移和所属偏移槽、不发送风扇档命令。
- 未验证：寂静档的物理转速效果与重启恢复仍需真机同负载对照，结论回填
  `docs/oem-dchu-contract.md` §11-9。

### 2026-11-23 审查修正

追加隔离验证覆盖档位变化、软件接管、能力未知和固件能力禁用，核对拒绝后保存字段与首次基线未变。 控制模拟器补齐生产模式驱动使用的 Windows 设备属性编译特性，四项监护交接检查通过。

面板、偏移许可和恢复基线共用有效风扇档位，解析娱乐档的寂静覆盖时核对 Turbo，档案仍捕获原始保存档。手动提交绑定有效档位和分档记忆槽，共用槽按固件映射归一，提交时从同一设备状态生成保存补丁。先写即时偏移，保存失败时重新下发本次写入前的保存偏移，并独立呈现补偿结果。

原生回归覆盖娱乐寂静的有效档位、旧记忆槽拒绝、部分保存失败与补偿失败、Turbo 生效时恢复基线，以及严格提交契约。页面回归覆盖娱乐寂静的面板与提交、预读后切档的错误回读和重试。

### 2026-11-24 固件侧核对

只读导出本机 DSDT（SHA256 与 `docs/oem-dchu-contract.md` §8 一致）静态反编译，并补审原厂
FnKey 7.19.5：

- 档位与偏移在 AML 中互不相干：`DCHU.SCMD` 0x79/0x01 发 EC 命令 0xD7 写档位位图（自动
  0x02、寂静 0x40 等），0x79/0x0E 直接写 EC 字段 `GFOF`（RAM 窗口 0xE7）。`GFOF` 全表只有
  这两处写入，AML 不读、切档不清。
- 因此「寂静档是否叠加偏移」只取决于 EC 固件内部，AML 没有可查的门控或互锁。原厂软件侧
  的证据到此穷尽：FnKey 恢复顺序为偏移在前、档位在后；Fn 键循环回自动且寂静偏好开启时只
  补发 `sub1=8`，不重发偏移；`page4[5]=8` 时原厂设置页显示自动单选并保留偏移滑杆。
- cmd13[14] 是 EC 命令 0xD7 的读回值（档位位图），不是偏移错位。

残留项（EC 在 0x40 位下是否消费 `GFOF`、重启后是否恢复）无法由静态分析回答。按既有流程
打包为批探测 `ccc-probe fan-offset-ab`：固定负载下依次测 自动/偏移 0 → 偏移 X → 偏移 0，
再测寂静档同一序列，自动档作为阳性对照；只发运行时命令、不写 AppSettings，结束或 Ctrl+C
后恢复原档位与偏移。探测的写入路径尚未在真机执行。

## 备选方案

- 保持仅自动可调：与已确认的原厂行为不符，且用户在寂静下无法完成原厂支持的调整。
- 在共享 `fanctl::set_offset` 全局按档位拒绝：会波及预设模式与恢复路径。
- 对齐原厂在 bit10 置位时清零：引入额外硬件写入，收益仅是状态整洁，不做。
